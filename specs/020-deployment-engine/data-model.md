# Data Model: Deployment Engine MVP

## Deployment Request

Represents one validation, dry-run, or apply invocation. Phase 1 carries request-specific fields through the existing engine inputs plus `DeploymentExecutionContext`.

Fields:

- `DeploymentId`: Stable identifier generated by the engine or supplied by caller.
- `Mode`: Validate, diff, dry-run, or apply.
- `Artifact`: Artifact identity associated with the desired state.
- `Target`: Host-agnostic deployment target descriptor.
- `Actor`: Optional caller identity for apply history.
- `Resources`: Desired deployable resources.
- `Prune`: Whether resources managed by the engine but absent from desired state may be deleted.

Validation:

- Target is required.
- Artifact identity is required by existing result/plan contracts.
- Resource identities must be unique.
- Prune defaults to false.

## Deployment Execution Context

Per-run transport-agnostic context passed to engine operations.

Fields:

- `Actor`: Optional `DeploymentActor` for audit history.
- `Prune`: Defaults to false; when true, managed resources absent from desired state may be planned for delete by handlers that can read managed state.

Rules:

- Future fields must remain host-neutral.
- Context must not include CLI/API-specific request objects.

## Deployment Resource

Existing abstraction representing desired control-plane state.

Important fields:

- `Id`: Stable type/logical ID/scope identity.
- `Version`: Optional desired version.
- `DesiredStateHash`: Optional hash used for idempotent comparison.
- `Dependencies`: Optional resource dependency identities.
- `Deletion`: Resource-level deletion behavior.
- `Metadata`: Extension metadata for handlers.

Validation:

- `Id.Type` and `Id.LogicalId` are required.
- Runtime state resources are forbidden.
- Handler for `Id.Type` must exist before apply.

## Deployment Plan

Deterministic description of proposed changes for one target and artifact.

Fields:

- `Id`: Plan identifier.
- `Artifact`: Desired artifact identity.
- `Target`: Target descriptor.
- `Changes`: Ordered change list.
- `Diagnostics`: Plan-level diagnostics.
- `CreatedAt`: UTC timestamp.

Ordering:

- Changes are ordered by resource identity string unless a future dependency-ordering decision replaces this rule.

## Deployment Change

Represents one proposed resource operation.

Fields:

- `ResourceId`: Target resource identity.
- `Action`: Create, update, delete, no-op, unsupported, or conflict.
- `Status`: Pending, ready, blocked, skipped, completed, or failed.
- `Reason`: Human-readable reason.
- `Diagnostics`: Change-specific diagnostics.
- `Resource`: Optional desired resource snapshot carried with the plan so dry-run and apply can operate without re-reading the artifact.

State transitions:

- Validation creates blocked changes for unsupported or invalid resources.
- Dry-run returns ready/skipped changes without mutation.
- Apply transitions ready changes to completed or failed resource results.

## Deployment Result

Outcome for validation, dry-run, or apply.

Fields:

- `DeploymentId`
- `Mode`
- `Status`
- `Artifact`
- `Target`
- `Plan`
- `ResourceResults`
- `Diagnostics`
- `StartedAt`
- `CompletedAt`

Status rules:

- Validation failures produce `ValidationFailed`.
- Dry-run with only no-op changes produces `NoOp`; otherwise `DryRunCompleted`.
- Apply with all changes completed produces `Applied` or `NoOp`.
- Apply with at least one failure and at least one success produces `PartiallyApplied`.
- Apply with all applyable changes failed produces `Failed`.

## Deployment History Record

Append-oriented audit entry for apply attempts.

Fields:

- `DeploymentId`
- `Artifact`
- `ManifestDigest`
- `Target`
- `Actor`
- `Status`
- `Plan`
- `ResourceResults`
- `Diagnostics`
- `StartedAt`
- `CompletedAt`

Rules:

- Recorded only for apply attempts in Phase 1.
- Recorded even when apply partially fails.
- Must not imply rollback unless handler results explicitly report compensating behavior.

## Resource Handler Registry

In-memory mapping from resource type to handler.

Rules:

- Resource type matching is ordinal and case-sensitive.
- Duplicate handler registrations for the same type are invalid.
- Missing handler creates diagnostics and blocks apply for that resource.
